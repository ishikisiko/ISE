## 1. 摘要与决策状态

本系统评测的是 **LLM 驱动 coding Agent 开发 ISE 的能力**，不是 ISE 自身的搜索、推理或回答质量。
用户要解决的问题是：在实际开发中，哪个模型能够更可靠地理解需求、完成改动、避免回归，并减少人工救场。

首版框架如下：

```text
固定任务 + 冻结代码快照 + 冻结环境 + 公开开发条件
                         |
                管理端调用 run
                         |
          启动用户选定 CLI，在隔离区开发
                         |
                       submit
                         |
                  冻结提交产物
                         |
                       grade
                         |
           干净环境重建 + 独立脚本验收
                         |
              自动基础分 + PASS/FAIL
                         |
               可选人工评审与加分
                         |
             JSON / Markdown 对比报告
```

| 状态 | 内容 |
|---|---|
| 已确定 | 固定起点、固定任务、独立验收、量化基础分、可选人工加分 |
| 用户明确 | 模型/CLI 由用户选，管理 Agent 可通过命令行启动 Codex/pi/Claude；不要求预先选名单，不设模型自评 |
| P0 决定 | 首版 `agent-native`，60/25/15 与人工最高 10 分，首批两题预算、隔离及评审责任见决策记录 |
| 归因边界 | 用户关注 LLM 开发效果；自由 CLI 成绩代表模型与 CLI 的组合，不直接当作模型本体排名 |
| P1 待验证 | 各题详细输入域、参考实现、镜像可运行性和初始配额；变更须在正式试跑前修订版本 |
| 尚未完成 | 框架代码、基准分支、导出快照、私有裁判、参考实现资格验证、模型实测与排行榜 |

本文所示命令、目录、JSON/YAML 均为拟定接口或结构示例。带有 `UNSET` 的字段必须在发布前替换；
正式模式必须拒绝未冻结、未准入的任务，而不是用隐含默认值运行。

## 2. 目标、边界与非目标

### 2.1 核心目标

给模型一份 ISE 代码和明确开发需求，在预先规定的工具、时间与资源条件下，测量：

1. 是否真正完成目标行为，而不只是增加几个函数或修改说明。
2. 是否接入真实 CLI、HTTP、流式接口、前端或执行链，具体范围由每道题规定。
3. 是否保留既有行为、状态一致性和关键安全约束。
4. 是否能够自己发现错误、编写有效测试，并诚实报告验证结果。
5. 是否需要用户指出漏项、定位错误或提供修改方法。
6. 获得可靠交付所花费的时间与费用，包括失败尝试。

“一次交付”允许 Agent 在自己的开发阶段反复编辑、自测和调试，指的是 **第一次正式提交前不需要人工纠错**，
不是只允许一次模型调用、一次代码编辑或一次测试。

### 2.2 两层模型必须隔离

```text
被测外层：LLM -> coding Agent -> 阅读/修改/测试 ISE 代码
固定内层：ISE -> scripted LLM / fake provider / 固定文档 / 临时 SQLite
```

ISE 内部模型调用、搜索响应、时间、数据库初态等应由确定性夹具控制。外层模型变更时，内层条件不跟着变。
真实 provider 烟测可作为补充实验，不能混入确定性开发基础分。

### 2.3 非目标

- 不构建通用 LLM 智力榜，也不宣称单个仓库的结果能代表全部软件开发能力。
- 首版不要求各模型从零重写 ISE；架构差异过大时，成本和归因难度都显著增加。
- 不以 ISE 的答案正确率、Hit@K、MRR、回答文采作为开发得分。
- 不以修改行数、文件数量、解释长度、测试数量或“看起来很努力”计分。
- 不把 LLM judge 作为功能正确性的最终裁判。
- 不设置被测模型自评或自动主观加分步骤。
- 不强制复刻参考实现的类名、内部函数、文件拆分或补丁形状。
- 不自动将候选代码合入 ISE `main`，也不自动推送任何分支。
- 不重写外层 CLI 的推理循环或模型 API 适配器；只做进程调度与验收，不先建设排行榜 Web UI。

现有 [baseline_runner.py](../../tests/baseline_runner.py) 和
[搜索质量评测](../guides/search_quality_evaluation.md) 针对运行中的 ISE。新的 `devbench` 不应混用这些结果作为开发分数，
最多复用通用的结果记录思路。

### 3.2 不可直接继承的假设

- 历史测试通过不等于当前镜像能复现，也不等于某道新题有完整验收覆盖。
- 现有测试可能与实现耦合，或只间接证明目标行为。例如当前
  `test_cancel_does_not_leave_unanswered_tool_call` 最终断言取消状态，未直接断言运行后 checkpoint 的消息配对。
- 历史大提交不等于单一任务。`f2f88fd` 修改 51 个文件；`1a512ed` 同时包含自主度、取消、澄清和其他行为。
- 当前架构不能倒灌到所有旧快照中作为隐藏要求。每道历史题需要自己的可见规则包与回归范围。
- `config.json`、`uploads/`、`checkpoints/`、`runtime/`、日志和用户记忆可能包含秘密或答案信息，不能复制到考场。
- `environment.yml` 的名称是 `env1`，但仅环境名称相同不代表依赖相同。历史快照是否兼容当前锁文件尚待验证。

## 4. 评测轨道与可比性

### 4.1 运行轨道与正式资格

| 轨道 | 固定与变化 | 用途 |
|---|---|---|
| `agent-native` | 领取任务后使用自己选择的 CLI，登记可获得的模型、工具与配置信息 | 首版默认，比较实际开发表现，不能把差异全部归因于模型 |
| `model-controlled` | 额外固定框架、工具、可见资料与开发策略，只替换模型及必要协议适配 | 未来可选的模型归因实验，不阻塞首版 |
| `practice` | 可使用工作树、查看隐藏反馈、自由调试 | 出题和流程调试，不进入正式榜 |

首版默认执行方式为 `managed-cli`：用户指定任务与运行配置，管理 Agent 经确定性启动器调用相应 CLI。
备用 `manual-external` 保留给用户自行启动或尚未适配的 CLI。两者都使用相同的提交与验收契约。
模型名单不属于框架准备的前置条件；缺少模型 API 适配器或完整 usage 不阻止领取任务和评分。
手填模型信息标记 `operator_declared`，不能凭一个模型名称就进入受控模型榜。
管理运行另外记录 profile、CLI 探测、启动参数摘要和实际事件来源，不把 CLI 自报当作独立 provider 证明。

轨道与隔离是两个维度：`agent-native` 可在 `local-practice` 下得到单次诊断分，
但只有经验证的 `isolated-formal` 运行才具备正式比较资格。能复验代码不等于能证明开发阶段没看到答案。

### 4.2 每次运行需要固定或登记的条件

- 模型 provider、精确模型标识、可获得的版本、推理设置、温度和上下文上限；不可获得的字段写 `unknown`。
- CLI/Agent 版本、可获得的系统提示与工具信息、上下文压缩策略、skills、是否允许子 Agent；不要求专有内部信息可见。
- 同题同一套代码、需求、项目规则、公开测试、开发期模拟服务和允许访问的文档。
- 执行时间、CPU/内存/磁盘/进程数限额、网络策略与依赖策略；调用计数仅在可采集时附报，不假设任意 CLI 都能强制计数。
- 澄清规则、纠错反馈规则和正式提交次数。

首版正式配置禁用子 Agent 与个人记忆，减少变量；不兼容者仍可练习。未来放开时另建运行配置并披露子调用统计覆盖率。
推理档位名称和 token 数并不天然代表跨模型的等价算力，不以“同名 high”或“同 token 数”宣称严格等算力。
同一参测对象在重复运行间保持 CLI、模型和设置一致；不同对象的 CLI 可以不同，这是 `agent-native` 的比较变量。
首版使用共同墙钟及资源预算，费用/token 单独报告；缺失字段为 unknown/null，不作为 0。
框架不承诺控制用户外部 CLI 的花费，等成本实验另设档位。本期只离线准备，不安排真实模型试跑。
未来管理端启动 CLI 同样可能收费，必须绑定用户批准的任务/profile/次数/时限，不能从设计请求推定运行授权。

### 4.3 重复与反馈

正式初步筛选按每个参测配置、每道题独立运行 3 次，清空会话和文件状态，保存全部结果，不挑最好一次。
单次领题不要求预先确定整批名单；缺少足够重复或可比条件时只显示单次/暂定结果。
3 次只用于发现明显差异，不能据此宣布小分差具有统计显著性。

若用户选择一轮纠错扩展，正式无救场运行完成后，可复制其提交进行一次“标准化纠错”实验：只给预先定义的问题现象，不给私有测试源码或修改方案。该扩展不属于首版必做功能。
该实验有独立 run ID、父提交和额外预算，不覆盖第一次成绩。

需求澄清与纠错分开记录。前者询问任务未明确的产品语义，后者需要用户指出实现遗漏或错误。
新澄清若改变原先验收要求，应升级任务版本并让全部模型使用相同新条件，而不是只给某次运行补充要求。

## 5. 逻辑架构与信任边界

```text
[出题与控制区：可信]
  task registry / source snapshots / reference code / hidden expectations
  management interface / job supervisor / CLI adapters / scorer / artifact store
            | 仅公开任务、净化后的代码和开发资料
            v
[开发工作区：不可信]
  coding Agent 的工具执行进程
  独立 Git 仓库 / env1 开发环境 / 本次运行的临时数据
            | 仅提交封装后的代码产物，不接收它自报的分数
            v
[候选执行区：不可信，每次 grade 重建]
  base + submission / frozen env1 / ISE 子进程
            ^ 请求、模拟响应、逐例输入
            | 输出、外部观察、调用轨迹
[验收与评分区：可信]
  持有预期值的测试驱动 / mock gateway / browser driver / scorer
            |
       不可变的 grading result
```

### 5.1 组件职责

| 组件 | 职责 | 不应承担的职责 |
|---|---|---|
| Task Registry | 任务版本、公开契约、私有验收映射、权重、准入状态 | 运行期间接受 Agent 修改评分规则 |
| Snapshot Builder | 导出精确代码、清理答案与秘密、生成源文件清单和摘要 | 默认把整个主仓库挂进考场 |
| Management Skill | 把用户请求映射为受控命令、展示进度与报告 | 给参赛者补解题建议、临时生成评分规则 |
| Workspace Preparer | 建立独立工作区、环境与 run manifest，交给选定 CLI | 自动选择最新分支头、替用户选择模型 |
| CLI Adapter | 按固定版本生成 argv/输入并解析事件，首批 Codex/pi/Claude | 重写 CLI 推理循环、自动 fallback 模型、输出评分 |
| Job Supervisor | 授权核验、启动、时限、停止进程树、幂等与日志收集 | 未授权调用 CLI、依赖管理 Agent 在线才能终止进程 |
| Submission Collector | 停止写入、收集新增/修改/删除/二进制资源、冻结产物 | 信任候选工作区的 Git 状态或自报提交范围 |
| Evaluation Driver | 重建候选程序、发送验收输入、获取独立观察 | 在可信主进程 import 候选 Python 代码 |
| Scorer | 按冻结规则计算得分、状态、覆盖完整性 | 用候选 stdout 中的“passed”或分数作为事实 |
| Review Manager | 绑定评审、校验加分范围与证据、保存修订 | 通过人工加分改变自动 PASS/FAIL |
| Reporter | 单次报告、分项比较、无效运行与费用披露 | 丢弃失败记录或自动选最好结果 |

### 5.2 隔离级别

| 级别 | 机制 | 可作何种结论 |
|---|---|---|
| `local-practice` | 本地独立目录或 worktree，可能共享用户权限 | 调试流程；不声称隐藏题或参考答案真正隔离 |
| `isolated-formal` | 净化快照、独立 Git、受限开发容器、独立执行容器、外部评分控制器 | 正式工程能力比较的目标级别 |
| `hardened` | 独立虚拟机/主机、进一步约束内核与服务攻击面 | 未来面向不可信参赛方的扩展，不属于首版完成条件 |

容器不是绝对安全证明。正式报告记录实际隔离级别与限制，不能把目录名或只读标记当成安全边界。
管理 Agent 运行在可信控制端，被测 CLI 在不可信开发区；二者可以使用同一品牌 CLI，但不能共享会话、HOME、秘密或权限。
固定启动 prompt 由公开任务包生成，不接受管理 Agent 的自由改写，避免管理端成为隐形解题助手。

## 6. 分支、版本与快照设计

### 6.1 分支用于管理，内容标识用于复现

`bench/ise-v1` 可以作为维护者理解的入口，但一个 suite 可能包含不同年代的代码起点。
最终运行必须读取 suite 清单中的每题固定对象，而不是执行 `checkout bench/ise-v1` 后默认所有题共用该代码。

需要区分：

- `source_commit`：来自 ISE 历史的完整提交 SHA。
- `base_revision`：出题方准备后的试卷版本，可包含必要的环境修复或净化记录。
- `base_snapshot_digest`：实际交给 Agent 的源文件内容清单摘要，才是考场代码的最终身份。
- `public_bundle_digest`：需求、规则、公开测试与文档的内容摘要。
- `reference_revision`：私有参考实现版本，不向被测 Agent 公开。
- `grader_revision` / `grader_digest`：私有判定器与验收清单身份。
- `environment_digest`：镜像及运行配置身份，开发和验收镜像分别登记。

仅有 SHA 不能提供保密性；只有摘要没有可信存储也不能提供真实性。控制器保存不可修改的发布清单，
并验证下载或恢复的内容与发布记录匹配。

### 6.2 推荐的仓库与分支布局

ISE 保持正常开发，本文及公开方法说明可以放在 ISE 文档目录。题库控制、参考代码和正式运行产物放在独立私有区域：

| 仓库/区域 | 分支或对象 | 作用 |
|---|---|---|
| ISE 主仓库 | `main` | 日常产品开发，不作为可移动的正式题目身份 |
| 私有 `ISE-devbench` | `main` | 框架、任务清单、发布规则 |
| 私有 `ISE-devbench` | `bench/ise-v1` + 不可覆盖的 `suite/ise-v1.0.0` 标签 | suite 清单与发布入口，不混入某一个 ISE 起点 |
| 私有源快照仓库 | `bench/base/T01/v1` 等 | 按题准备与审核代码起点 |
| 私有源快照仓库 | `bench/reference/T01/v1` 等 | 从对应 base 派生的参考实现 |
| 私有源快照仓库 | `bench/mutant/T01/<case>` 等 | 故意错误的对照实现，仅出题方可见 |
| 每次开发工作区 | `run/<run_id>` | 新初始化 Git，只含该题净化起点与本次 Agent 改动 |
| 产物存储 | `runs/<run_id>/submissions/<digest>` | 正式计分依据，不依赖工作分支是否继续移动 |

上述分支均未创建。“同一个 Unix 用户下换个目录”不能满足私有区域不可访问的要求。
P0 已选定同机私有存储加受限容器的首版方案，路径、可信主体及分支归属见
[部署决策](p0_decisions.md#storage)，实际部署仍属于 P1/P2。

不在可供 Agent clone 的远端同时发布 base 与 reference。删除 reference 分支也不等于删除其对象、reflog、
stash、其他标签或归档中的答案。

### 6.3 base 的制作流程

1. 在可信准备区解析完整历史 SHA，导出受控文件树；Agent 不接触原仓库对象库。
2. 检查 `.gitattributes` 导出规则、符号链接、子模块、LFS 指针及二进制资源，不能默默漏文件。
3. 依预先审核的策略移除秘密、运行数据、Agent 会话、参考补丁、本分析文档及其他解题资料。
4. 保留与历史快照一致的正常项目文档和公开测试。必要的规则更正明确列入公开文件，不能悄悄附加未来约束。
5. 若必须修复环境或无关基线问题，作为独立 preparation patch 记录和复核，不得顺便实现目标功能。
6. 生成按路径排序的内容清单，记录文件类型、执行位、大小与 SHA-256；安全处理删除和符号链接。
7. 在开发沙箱中新建 Git 仓库，用固定身份生成一个起始提交，不配置原仓库 remote、alternates 或共享对象库。
8. 验证工作区只包含允许的资料和本地历史，然后发布 base snapshot digest。

`git worktree` 会与原仓库共享仓库信息，适合可信准备区并行整理题目，不适合作为参赛隔离机制。
这一点来自 [Git worktree 官方说明](https://git-scm.com/docs/git-worktree)；本系统因此采用导出快照后重建独立 Git 的方案。

### 6.4 版本冻结和变更

- `draft -> qualifying -> frozen -> retired` 是任务生命周期；只有 `frozen` 可用于正式排名。
- 发布后禁止移动标签或覆盖同一版本产物。改变需求、权重、必过项、有效输入域、环境或验收语义都需要新版本。
- 修正有缺陷的 grader 时保留原结果与原因，用新 grader 对所有保留提交统一重评，不只重评某个模型。
- 重评不提供额外开发机会。使用旧题结果与使用新题结果必须分榜或标明版本。
- 基准分支不合并回 ISE `main`。参考实现若确实对产品有价值，走普通评审与合入流程，并将对应题标注为已公开答案。
- 新功能题一旦参考实现公开，只能作为公开历史题，不能继续声称它是未见过的新需求。

## 7. 环境、网络与秘密隔离

### 7.1 环境冻结

项目运行在名为 `env1` 的 Conda 环境。镜像构建使用对应 base 的依赖声明与经过实际验证的锁定结果，
记录 Python、系统库、浏览器、依赖包、模型资源和构建脚本的版本及摘要。

建议使用两个相关镜像：开发镜像提供编辑、Git 和公开测试工具；验收镜像只含冻结运行依赖和必要驱动接口。
两者必须满足相同的应用运行契约，不能开发时可用、验收时故意缺少公开允许的依赖。

- 预下载固定 embedding 模型等必要资源，登记内容摘要；不在评分时从公网抓取最新版。
- 每道历史题单独进行环境资格验证，不能假设当前锁文件适用于旧代码。
- 新依赖默认不允许随意联网安装。任务确实需要时，公开允许包集合与固定镜像源，安装变更进入提交并在干净环境复现。
- 每次运行新建临时 SQLite、上传目录、缓存目录和浏览器 profile，不使用用户真实数据。
- 同题所有模型使用相同硬件资源配额；执行顺序随机化或交错，记录资源争用，避免机器负载与模型身份相关。

### 7.2 沙箱配置要求

正式开发与执行区使用非特权进程；不挂载主仓库、用户主目录、云凭据、SSH/Git credential helper、
Docker socket、宿主进程命名空间或控制器产物目录。限制进程数、内存、CPU、磁盘和执行时间。
默认移除不必要 capabilities，使用适用的系统调用约束，并禁止提权。

这些是部署验收项目，而不是本文已验证的配置。容器仍有内核、daemon 和挂载边界风险，需结合
[Docker 安全文档](https://docs.docker.com/engine/security/)审核实际部署；需要更强对抗保证时升级到独立虚拟机。

### 7.3 网络策略

| 主体 | 允许访问 | 默认禁止 |
|---|---|---|
| 可选外层模型网关 | 用户所用 CLI 必需且批准的 provider | 将真实 provider 密钥交给候选代码或开放无界通用代理 |
| Agent 工具执行区 | 本次工作区、开发期 mock、固定文档或批准的包镜像 | 原仓库远端答案、参考代码、裁判服务、宿主敏感网络 |
| 候选 ISE | 本次验收 mock gateway 和必要的本地服务 | 公网搜索、真实 LLM、云 metadata、其他 run 的服务 |
| 可信验收驱动 | 本次候选服务、artifact store | 执行候选提交中的任意控制脚本 |

在出口代理或网络命名空间实施策略，不依赖候选程序自己遵守。重定向、DNS 与绕过代理路径也要覆盖。
正式 CLI 接入不得挂入宿主登录资料；真实 provider 凭据保留在候选区之外。
兼容 CLI 可使用外部网关提供的本次运行连接，框架不必托管模型调用。若 CLI 与工具共享沙箱，
短期连接凭据可能被候选代码读取，不能宣称保密；其权限须限本次运行、限用途并能撤销。
不满足正式条件的 CLI 可继续使用练习入口，不承诺任意 CLI 无配置即可安全接入。
独立验收区只看到合成测试配置和本次 mock，没有外层模型网关权限。

### 7.4 文件与过程信息

公开资料包中的 `AGENTS.md`、skills 和文档必须冻结并对所有被测模型一致。
不同历史 base 可以有不同规则，但不能把最新项目规则不加审核地塞回旧快照。
不继承当前会话、个人记忆、编辑器历史、shell history 或此前运行的答案。

共享缓存只允许只读、校验内容的公共依赖；不能跨 run 共享模型回答、源码构建缓存、pytest cache 或 checkpoints。
Agent 运行日志属于受控数据，报告默认脱敏，不对其他参赛运行开放。

## 8. 任务包、参考实现与准入

### 8.1 每题三件套

| 产物 | 必须证明的事情 |
|---|---|
| `base` | 可以开发和运行；指定既有回归基线已知；目标能力尚未全部成立 |
| `reference` | 至少一种合理实现能够在规定环境中满足全部自动验收 |
| `grader` | 能抓住缺失或错误行为，也能接受不复制参考代码的合理实现 |

参考实现是必要的可完成性证据，不是唯一标准答案。不要求先把整个 ISE 修到没有任何问题，
但每道题必须公布和冻结其相关的已知基线问题与回归排除项。
任何新增失败不能在看到被测提交后临时解释为“原来就有”。

### 8.2 公开与私有内容

公开：自然语言任务、范围与非目标、输入输出契约、必要安全和兼容约束、评分权重、必过项、预算、公开样例、
已知基线问题、可用命令、依赖规则、开发期模拟服务协议。

私有：完整隐藏样例、预期结果、参考实现、错误对照实现、内部映射脚本、完整 qualification 记录。
公开权重不等于公开所有测试输入；隐藏样例不能引入未说明的产品语义。

不得把本系统分析文档当成任务书直接分发。历史参考 SHA、具体修复思路、mutation 策略、其他候选题都应留在控制区。

### 8.3 准入流程

```text
需求/范围/评分点 -> 验收设计 -> 参考实现 -> 三类对照验证
                                           |
                      base 未满足目标 + reference 满分 + mutants 被识别
                                           |
                           独立复核 / 合理替代实现检查
                                           |
                            干净环境重复验收与隔离检查
                                           |
                                      冻结发布
```

首版建议为每题至少准备三类错误对照：遗漏目标行为、破坏边界、引入回归。
“删除所有校验”“只隐藏工具名”“硬编码公开样例”应当是优先验证的对照类型。
对照实现不是参赛者任务的额外要求，只用于证明验收能识别已公开契约的违反。

简单题可制作另一种参考实现；复杂题至少由独立复核者检查隐藏测试没有不必要的实现绑定。
首版参考验收建议在干净环境重复 3 次，要求得分、判定和稳定字段一致；并发与状态题需增加不同调度序列。
这只是准入下限，不构成无 flaky 或覆盖完备的证明。

## 9. 自动验收设计

### 9.1 提交冻结

`submit` 的含义不是要求 Agent 必须会提交 Git，而是由控制器捕获 **实际源文件产物**：

1. 停止开发会话及相关写入进程，冻结本次文件系统视图。
2. 与控制器保存的 base manifest 比较，不信任工作区可被修改的 `.git`、`.gitignore` 或 `git diff` 输出。
3. 收集允许范围内的新增、修改、删除、执行位与二进制资源；忽略项使用控制器冻结规则。
4. 拒绝路径穿越、指向控制区的符号链接、设备文件、超限文件或未声明的外部依赖。
5. 产出完整提交归档、可读 diff、文件 manifest 与 `submission_digest`，保存在模型不可写的区域。
6. 后续修改必须产生新的提交对象与 run；不能在旧结果下替换代码。

任务可以允许修改已有测试，但独立验收和保留回归来自控制器的受保护副本。
删除、skip、弱化工作区里的测试不能减少正式验收范围。也不能一律禁止改测试，否则会错误排除正常开发工作。

### 9.2 干净重建与完整性检查

验收从冻结镜像、base 与 submission 重建，不复用开发时的虚拟环境、数据库、缓存、监听端口和临时修改。
同一提交的重评创建新 `evaluation_id`，保留相同 `submission_digest`，不能覆盖旧日志。

控制器验证预期验收项数量、ID、顺序约束及结果完整性；未知项、重复项、缺项和提前终止均须明确分类。
固定非测试相关环境变量，隔离候选 `PYTHONPATH`、pytest 插件自动发现、`conftest.py` 和 `sitecustomize.py` 对裁判的影响。

### 9.3 黑盒为主，白盒为辅

正式功能分优先由控制区驱动 HTTP、CLI、浏览器和模拟 provider，断言最终输出、持久化状态和实际调用。
必要的公开 Python API 可以通过执行区的受限适配进程调用，只传递结构化数据；预期值和判定仍留在控制区。
不在可信评分进程 import 候选模块，也不反序列化候选提供的 pickle 或执行其报告脚本。

必须承认边界：**隐藏 pytest 与任意候选 Python 代码放在同一进程里，无法仅靠只读挂载保证测试保密或结果可信。**
反射、导入钩子、插件和伪造输出都可能干扰验收。单独的结果签名也不能修复“签名了伪造输入”的问题。

因此：

- 私有完整测试集、预期答案和结果目录不挂进候选执行区。
- 黑盒驱动逐例发送必要输入，不一次暴露整套隐藏样例；评分来自外部观察，不接受候选自报通过。
- mock provider 的真实调用记录由控制区保存，与候选内部 trace 对照，不单凭候选 trace 证明没有越权调用。
- 白盒测试可作为辅助证据；某验收点只能依赖不受保护的进程内断言时，须标记较低可信度并在正式发布前补强。
- 对验收规避、按测试环境硬编码等情况进行独立审查；范围内的行为优化与正常替代实现不应被误判为作弊。

### 9.4 验收层次

| 层次 | 验证内容 | 证据 |
|---|---|---|
| 产物与构建 | 源文件完整、依赖合规、干净导入/启动 | 构建日志、hash 校验、进程退出信息 |
| 目标功能 | 需求所指定入口真正可用 | HTTP/CLI 输出、文件下载、协议结果 |
| 边界与安全 | 无效输入、回退、隔离、预算、禁止路径 | 外部 provider 计数、返回码、状态快照 |
| 回归 | base 中指定需保持的行为 | 冻结回归集、前后状态对照 |
| 交互 | 按钮、错误态、下载、取消、会话续用 | 浏览器事件、DOM 断言、截图与网络日志 |
| 验证可信度 | Agent 的完成与测试声明有证据支持 | 命令记录、测试产物、最终交付说明 |

UI 功能正确性应自动验收，不留给人工加分兜底；视觉融合、布局品质等可进入人工项。
应用内部模型使用脚本化响应，同时提供多个等价场景，避免只适应唯一固定工具调用序列。

并发测试使用可控 barrier/event 和明确超时，不以偶然 `sleep` 调度判分。
超时必须区分应用自身不终止与测试设施故障；所有子进程和端口在结束后清理，并检查残留。

### 9.5 失败分类

| 情况 | verdict / 处理 |
|---|---|
| 所有必过验收达标，完整性检查通过 | `PASS` |
| 功能错误、关键回归、违反公开边界 | `FAIL`，保留诊断分与失败证据 |
| 无改动或未完成 | `FAIL`；不能把“原有测试通过”当作完成任务 |
| Agent 超出开发预算或主动放弃 | `FAIL`；可验收截止时已冻结的最后产物，不能获得额外开发时间 |
| 候选改动导致无法安装、启动、测试发现被破坏 | `FAIL`，不是基础设施异常 |
| 候选进程超出公开内存、磁盘或进程数配额 | `FAIL`，不能因运行节点杀死它而改记为设施故障 |
| 工作节点丢失、冻结镜像损坏、mock 服务本身故障 | `INVALID`，基础分为 null，登记原因并按统一规则重跑 |
| 根因不明的异常 | 暂记 `INVALID` / `triage_pending`，独立归因后追加修订记录，不能永久选择性排除 |
| 意外 skip、缺少必须执行的验收 | 根据根因标为 `FAIL` 或 `INVALID`，绝不算通过 |
| 检测到答案泄漏或裁判篡改 | `INVALID` / `integrity_violation`，取消排名资格并保留审计记录 |

应用安全规则被绕过属于代码失败；开发环境完整性或评测协议被破坏属于评测完整性问题，两者不要混为一谈。
无提交导致无法启动时自动分可为 0；若仅部分组件失败，独立且可信的已完成验收仍可计诊断分。

<a id="scoring"></a>

## 10. 自动分数、通过状态与汇总

### 10.1 单题基础分

首版确定功能 60 分、边界 25 分、回归 15 分，每题总计 100 分。每个计分验收点是预先定义的行为单元，
不是动态收集出来的 pytest 用例数量。

```text
point_i = 1，当且仅当该验收点要求的全部条件成立；否则为 0
base_score = sum(weight_i * point_i)
sum(weight_i) = 100
PASS = 所有 required 验收点通过，且评测完整性与任务级硬门槛通过
```

验收点需要部分给分时，应在发布前拆成有固定权重的子项，而不是运行后根据失败数量自由分配。
多加十条同一边界的测试不能使其权重增长十倍。

本候选集默认六个计分验收点均为必过，因此全部通过对应 100 分；低于 100 的分数主要解释未完成程度。
未来可设置明确的非必过优化项，使 PASS 与满分不完全重合，但必须在题目发布前公开，不能为了制造分差临时增加。
初版不设置一个“达到 80 分即可无视硬失败”的通用及格线。

无改动提交可能因保留既有行为而得到少量诊断分，报告标记 `no_change`，不能计为完成。
不通过安全或关键回归的 95 分提交，不能被表述为“基本验收通过”。

### 10.2 两个主要客观指标

保留两个指标，而不是让单个总分承载所有含义：

1. **平均基础分**：描述平均完成程度，按任务等权，再在任务内平均各次独立运行。
2. **开发可靠性分**：`100 * 各任务独立交付成功率的等权平均`，描述无人工纠错时完整交付的频率。

```text
task_score(participant, task) = mean(base_score over valid scheduled runs)
task_reliability(participant, task) = mean(verdict == PASS over valid scheduled runs)
suite_score = mean(task_score over the frozen task set)
reliability_score = 100 * mean(task_reliability over the frozen task set)
```

只有任务集合、轨道、执行方式、版本、预算、正式隔离资格与有效重复数兼容时才给正式排序。
默认不把 manual-external 与 managed-cli 无提示混排；合并前须证明共同条件等价并公开口径。
`participant` 在首版表示 CLI、模型和配置的组合；配置变更视为不同参测对象，不伪装成同一模型的重复运行。
`INVALID` 不按零分混入能力分，但必须报告数量、原因与补跑状态；未补齐时仅显示暂定结果，不用较小分母制造领先。
模型自身失败、超时和未完成仍在有效计划运行的分母里，不能因为没有结果文件就被丢弃。

首版客观表同时列基础分、可靠性分和关键回归数；按基础分展示时也不能隐去 PASS 频率。
小样本仅做筛选；扩展后提供按任务配对的差异、区间或 bootstrap，并避免把同一家族变体当作完全独立样本。

### 10.3 省心与效率辅助指标

| 指标 | 定义与限制 |
|---|---|
| 关键回归率 | 出现预先定义关键回归的有效运行占比 |
| 一轮纠错成功率 | 统一反馈和额外预算下修复成功的比例，单独报告 |
| 人工介入 | 澄清、提醒、定位、直接提供修改建议分类型记录；不把合理澄清一律处罚 |
| 验证声明失实率 | 明确声称完成/执行/通过的事项中，有记录证明不实的比例；日志缺失标为不可核实 |
| 时间 | 开发与机器验收分开记录，排队和设施故障不伪装成模型推理时间 |
| 费用 | 有完整来源时统计外层调用与重试总费用；不完整时标记覆盖范围，不宣称完整成本，成功数为 0 时单位成功费用为 null |
| token | 分 provider 记录实际使用与统计覆盖率；未捕获写 null，不当作零成本 |

代码质量、架构理解等能力标签可以从任务族与失败类型归纳，不对无法直接观察的“内在思考质量”打分。

辅助指标的唯一实现。被补跑替代的设施无效运行移出分母并保留原记录；缺结果、未补齐的设施无效或
有效次数少于预登记次数，任一出现即 `provisional` 且不给正式排名。小样本解释是封闭词表
（`insufficient_repeats`/`overlapping_results`/`provisional_inputs`/`screening_signal`），
不产生显著性、能力强弱或通用 LLM 排名的表述。详见[任务历史明细 P3-B](task_archive.md) 与私有

## 11. 人工评审与加分

### 11.1 规则

自动基础分最多 100，人工加分最多 10，总展示上限 110。人工项只能加在 `PASS` 且完整性检查通过的提交上，
不能补救功能未实现或安全回归。

| 人工项 | 分值 | 示例锚点 |
|---|---:|---|
| 可维护性 | 0-4 | 0：明显增加维护负担；2：符合现有结构且可读；4：在复杂部分有可证据支持的清晰处理 |
| 范围控制 | 0-3 | 0：大量无关改动；1：少量非必要扩张；3：边界清楚，没有为解题引入不必要框架 |
| 交付清晰度 | 0-3 | 0：难以判断改了什么；1：有基本说明；3：变更、验证与限制准确、可追溯 |

每题可在上述范围内细化解释，例如 T02 的可维护性与交付清晰度包括界面是否自然融入和错误态是否易懂。
核心 UI 功能仍属于自动分。人工规则在评审前冻结；不按文档长度、截图数量或新增功能数量加分。

尽量隐藏模型身份，评审者为每项提供代码、截图或日志引用。无法盲评时标记。
首版每份评审指定一人；未来多评审者使用事先约定的聚合规则，并保留原始分歧，不能择取最高分。

### 11.2 状态与重评

- 未评审：`manual_bonus = null`，不同于评审后 0 分。
- 不具资格：`review_status = ineligible`，不计算个人总分。
- 已评审：逐项校验范围与证据，`personal_total = base_score + manual_bonus`。
- 修改评审创建新 review revision，保留旧记录；不得直接改自动结果。
- 评审绑定 task、submission、evaluation 和 rubric 身份。代码或自动评估版本变化后必须重新确认，不能静默沿用旧分。

客观榜不受人工分影响。个人榜按明确口径显示总分，未评审记录不参与混排。
脚本可以重算和审计加分，但不能自动复现人的主观判断。

### 11.3 低负担评审入口

不设模型自评，也不把被测 Agent 的交付说明当成验收事实。自动评分不等待人工介入。
`review prepare` 生成一页摘要、分项验收、主要 diff、必要截图与证据索引，按需再展开原始日志。
PASS 后用户可直接跳过，或填写三个分项、短理由和已有证据 ID；身份/hash 自动预填，不要求手工拼装评审 JSON。
用户给分后可由助手代录，但助手不能自行赠分、伪装成人工签署或修改自动 PASS。

`review record` 校验分数范围、整数、完整项、证据存在性与提交身份，追加评审版本；缺省分数为 null。
报告默认隐去模型/CLI 身份，但记录实际盲评程度为 `false`、`partial` 或 `true`。
发现验收缺陷时转入独立裁判复核，暂停排名资格；不得用人工分覆盖自动结果。

P1 的题目资格复核由项目维护者负责最终验收，不能由同一参考作者自行签署；个人加分由用户或其指定者按需完成。
报告内容须转义并禁用候选注入的脚本/外链；候选应用预览保持隔离。
具体角色、操作与保留政策见 [轻量评审决策](p0_decisions.md#review)。

## 12. 运行状态、产物与命令接口

### 12.1 状态机

```text
PREPARED -> RUNNING -> SUBMITTED -> GRADING -> GRADED
                                        |       |
                                        |       +-> REVIEWED -> REPORTED
                                        +-> INVALID -> TRIAGED
```

开发超时由控制器冻结截止时产物，登记 `stop_reason`，再进入相应验收；没有产物也必须形成失败记录。
正式模式必须在首次交付可读任务前进入 RUNNING 并开始计时，不能让 PREPARED 成为无限制预读期。
本地练习中不能停止外部 CLI 的情况如实记录，不声称开发配额已经被强制执行。
`managed-cli` 的监督器独立持久运行；管理会话结束不取消计时。启动前不兼容/未授权记为 LAUNCH_REJECTED，
启动后故障保留运行记录并按统一规则归因；CLI 退出码或“完成”事件不能直接生成 PASS。
具体进程、事件、恢复与停止协议见 [CLI 生命周期](cli_orchestration.md#lifecycle)。
状态迁移和时间戳由控制区记录，不能接受候选工作区写入的“完成”文件作为唯一证据。
报告是对已保存事实的投影，重复生成不能修改原始 run、submission、evaluation 或 review。

### 12.2 私有控制仓库建议结构

```text
ISE-devbench/
  devbench/                  # CLI、控制器、快照、验证、评分、报告
  suites/ise-v1.yaml         # 每题版本与起点的冻结清单
  tasks/T01/
    task.yaml                # 完整任务清单，不直接发给 Agent
    public/                  # task.md、公开样例、规则、模拟协议
    private/                 # 验收映射、预期、qualification 记录
  environments/             # 镜像、锁定依赖与构建规则
  profiles/                 # CLI 版本、模型设置、权限与认证引用；不含密钥
  management/               # 管理 skill 的受控指令源，不进入考场
  schemas/                   # manifest、submission、result、review
  tests/                     # 框架本身的测试

private-artifacts/           # 与源码权限分离；不对 Agent 挂载
  snapshots/<digest>/
  references/<digest>/
  runs/<run_id>/
    run.json
    development/             # 工具/模型调用记录，按策略脱敏

    evaluations/<eval_id>/   # checks、provider trace、JUnit、screenshots

```

文件命名不能替代访问控制。若 private 子目录与 Agent 在同一权限范围内可读，该运行不能声称完成正式隔离。

### 12.3 拟定命令

以下为目标接口示例；P2 控制器、P3-A 评审与 P3-B 批次/比较均已落地，
实际参数以 `python -m devbench --help` 为准。在独立控制项目中使用其冻结工具环境；ISE 子进程仍运行于镜像中的 `env1`。

```bash
python -m devbench task validate --task T01 --version 1.0.0
python -m devbench task qualify --task T01 --version 1.0.0
python -m devbench agent probe --cli pi --offline
python -m devbench run --task T01 --version 1.0.0 --profile pi-work --run trial-001 --dry-run
python -m devbench run --task T01 --version 1.0.0 --profile pi-work --run trial-001 --execute --authorization approval-001
python -m devbench status --run trial-001
python -m devbench report --run trial-001
python -m devbench review prepare --run trial-001
python -m devbench review record --run trial-001 --file review.json
python -m devbench batch register --batch pilot1 --participants participants.json --organizer USER
python -m devbench batch freeze --batch pilot1 --approver USER --approval-reference REF
python -m devbench batch preregister --batch pilot1
python -m devbench batch execute --batch pilot1 --run trial-001            # 默认 dry-run
python -m devbench aggregate --batch pilot1 --leaderboards
python -m devbench compare --batch pilot1 --batch pilot2
python -m devbench smoke status --expect codex=<profile_digest>
```

- `validate`：仅校验任务结构、版本与依赖引用，不冒充资格测试。
- `qualify`：重建 base/reference/mutants，验证分数、硬门槛、重复性和完整性。
- `agent probe`：离线核对 CLI 安装、版本和参数，不能以帮助信息替代 live smoke。
- `run`：默认 dry-run；经实际授权后自动 prepare/launch/submit/grade/report，管理 Agent 不直接自由拼接被测命令。
- `status/logs/stop`：查询进度、读取脱敏事件和有界停止，不通过追加提示操纵参赛者的实现。
- `prepare`：拒绝未冻结任务，创建开发区和 run manifest；不要求先确定模型、提供密钥或实现 CLI 专用适配器。
- `submit`：冻结实际文件产物，记录内容身份和操作者声明的参测信息，禁止覆盖既有提交；模型信息缺失不阻止单次验收。
- `grade`：在新执行环境中验收；同一提交重评产生新 evaluation ID。
- `report`：从已保存的自动结果与有效评审生成报告，没有人工评审也可直接使用。
- `review prepare/record`：准备匿名证据包与空评分表，再校验并导入人工填写；不调用模型生成主观分。
- `batch`：登记参测配置与可观测声明、冻结批次条件、一次性预登记全部运行；结局成功与失败都保留，
  只有设施无效允许显式补跑，计划外运行不进汇总。
- `aggregate`：按任务等权计算平均基础分与开发可靠性分，同列关键回归数与辅助指标；
  缺结果或未补齐即标 `provisional`，不用较小分母排名。
- `compare`：拒绝不兼容版本、缺失运行与不同轨道的无提示混排；允许明确标记的暂定对比。
- `smoke`：登记真实 CLI/profile 隔离 smoke；无记录即 `unverified`，假 CLI 结果不能替代。

建议退出码：0 为操作成功且目标验收 PASS；1 为有效运行的验收 FAIL；2 为参数/清单错误；3 为设施或完整性导致 INVALID。
`report` 和 `compare` 的退出码表示操作是否成功，不能因为一份报告里有 FAIL 就误报报告生成失败。
后台 `run` 的提交成功仅表示作业已受理，最终判定从状态/报告读取，不能把后台启动退出码当作任务成绩。

### 13.1 T01：型号数字导致的引用误判

**给 Agent 的需求原型**：回答只提到产品型号或版本时，也被判定为缺少数值引用。修复此误判，
同时保留真实数值、引用有效性、来源权威性及必要时效检查。

**范围**：聚焦机械引用判定及其既有调用契约。不给“应修改哪条正则”的提示，也不要求修复同一历史提交里的
比较对象识别、重检索引导、第三方标注等其他问题。无需联网查询任何真实价格。

| 验收点 | 分值 | 自动证据 |
|---|---:|---|

### 13.2 T02：会话 JSON 导出

**需求原型**：用户可以在会话界面下载当前会话 JSON，包含标题、按顺序排列的问答及规定的来源字段。
当前已有会话读取、重命名和删除流程，任务应在此基础上扩展。

**拟定公开契约**：新增 `GET /api/conversations/<id>/export`，输出 `schema_version=1`、
`conversation{id,title}` 和 `turns[]`；每轮包含 `turn_index`、`query`、`answer`、`sources[]`。
来源仅允许公开的 `title`、`url` 字段。历史缺失来源转为空数组，不重新调用 LLM 或检索来补历史。
不存在的会话返回 404，存储不可用返回 503，响应行为和 JSON 错误结构在正式任务书中冻结。

无自定义标题时沿用列表的标题语义；无回答字段的旧轮次采用公开约定的空值策略。
来源 URL 的脱敏、缺 URL 来源的处理与不同历史 `result` 结构映射，必须在发布前用公开 schema 和样例明确。
不要误把“内部状态不导出”解释成删除用户问答中的原始文字；用户主动写入的敏感文本不在本题自动脱敏范围内。

**不做**：导入、完整 checkpoint 备份、批量导出、账户权限系统、重新生成历史答案。

**人工项关注**：操作是否融入既有界面、错误状态是否清楚、是否避免引入前端框架。
**准入待办**：补齐字段和错误协议、制作隔离浏览器镜像、指定桌面/移动测试 viewport，先做参考版本再冻结。

### 13.3 T03：文献元数据检索 Skill

**需求原型**：接入任务包提供的文献元数据服务，支持关键词检索，将结果接入现有工具、证据、来源与审计链。
不得另建只有独立脚本能运行的功能，也不考实际文献检索效果。

**拟定服务契约**：任务提供开发期 mock 和固定协议，例如 `GET /v1/papers/search?q=<query>&limit=<n>`，
返回 `items[]`，字段为 `id/title/authors/year/url/abstract`。错误状态、缺失可选字段和鉴权使用合成配置，
不得要求真实第三方账户。验收 mock 与开发 mock 使用同一协议但不同数据。

Skill 的公开工具参数优先沿用现有 `query` 形式，避免为考题强迫无关的工具封装重构。
名称、query 长度与规范化规则、可用性所需配置、调用/时间/证据上限均在任务发布时固定。
文献来源不能因为接入系统就自动被标记为官方权威来源；其来源类型按公开契约判定。

### 13.4 T04：请求级检索工具限制

**需求原型**：单次请求可以禁用指定检索工具，CLI、普通 HTTP 和流式 HTTP 行为一致，不影响其他请求。

**拟定契约**：HTTP 增加 `disabled_tools` 字符串数组，CLI 增加可重复的 `--disable-tool` 参数。
省略或空数组表示不增加限制；重复名称去重；未知工具或非字符串输入在调用 ISE 内部模型/provider 前拒绝。
合法名称集合在公开任务包冻结；已知但当前不可用的工具名可视为安全的无操作，不得顺便使其可用。
约定 HTTP 非法请求返回 400、CLI 参数错误返回非零，最终是否使用固定 2 号退出码在发布契约中明确。

本题按 **公开检索工具身份** 限制，不等于“完全禁网”。另一允许工具合法使用同一 provider，不应仅因 provider 名相同被误判。
裁判需要按工具请求和调用链关联；涉及同一 provider 的测试必须构造可明确归因的场景。
不得以别名、恢复路径或重新组装工具列表恢复已禁止的工具身份。既有 `--search off` 等限制只能收紧，不能被新参数解除。

限制属于本次请求，不写入全局配置或作为会话永久偏好；普通后续请求重新解析。
本题不额外要求设计澄清跨请求授权机制，相关边界应在任务书明确为保留旧行为或显式排除。

|---|---:|---|
| T04-F1：CLI、普通 HTTP、流式 HTTP 正确接收与传递限制 | 20 | 三入口等价输入矩阵 |
| T04-F2：工具面符合限制，其他允许工具仍能工作 | 20 | scripted LLM 观察工具面与调用行为 |
| T04-F3：即使模型尝试调用禁用工具，执行端也阻断实际调用 | 20 | 独立 mock 调用记录与结构化拒绝结果 |
| T04-B1：未知名称、非法输入、空值、重复名称处理正确 | 15 | 参数矩阵及拒绝前零调用断言 |
| T04-B2：连续、并发及同会话普通后续请求不串配置 | 10 | barrier 控制的请求交错与配置前后快照 |
| T04-R1：自主度、预算、preflight 和既有搜索限制不回归 | 15 | 冻结模式与工具执行回归集 |

**错误对照**：只改提示词；只在 `/api/answer` 生效；原地修改共享工具集合；复用 checkpoint 后恢复禁用工具。
**人工项关注**：策略传递是否清楚、是否保持请求局部性、是否避免到处散落同一检查。
**准入待办**：冻结名称集合、精确工具身份边界、同 provider 的归因夹具、澄清边界与并发预算。

### 13.5 T05：取消执行与会话续用

**需求原型**：用户可以取消正在运行的请求，得到明确的取消终态和已有部分结果，随后仍能继续使用同一会话。
从 `7e06917` 起步，只实现取消能力，不要求同时实现自主度、澄清或规划文本承载。

取消按公开约定的安全节点边界生效，不要求强杀正在进行的 HTTP 请求。
已经启动的工具工作应按边界契约结算和记录；不得留下未配对的工具消息或在取消后开启新的模型轮次。
完整一轮含多工具调用时，哪些调用已视为启动必须在任务书明确，不能靠隐藏测试临时定义。

|---|---:|---|
| T05-F1：run ID、取消 API 与界面停止操作形成实际闭环 | 20 | SSE/HTTP 与浏览器交互 |
| T05-F2：安全边界产生 cancelled 终态并保留已有证据 | 20 | 受控节点调度及外部结果 |
| T05-F3：取消后同会话可恢复并完成新请求 | 20 | SQLite checkpoint + 两次端到端请求 |
| T05-B1：预取消、结束后取消、未知 ID、重复取消符合约定 | 15 | 状态矩阵与模型/provider 调用计数 |
| T05-B2：无锁等待死结、消息配对正确、registry 不持续泄漏 | 10 | 锁与事件控制、实际 checkpoint 配对、清理检查 |
| T05-R1：正常问答、流式结束、会话恢复与审计不回归 | 15 | 历史 base 的冻结回归集 |

**错误对照**：只停止前端显示；取消接口等待被取消请求持有的会话锁；直接丢弃工具结果；取消后留下不可恢复状态。
**人工项关注**：状态转换是否易理解、资源释放是否集中、部分结果与终态是否清楚。
**准入待办**：从混合历史实现中抽取本题参考；补直接 checkpoint 消息配对断言，而非只判断 `cancelled` 字符串。

### 13.6 T06：上下文压缩与可靠恢复

**需求原型**：长会话逼近上下文预算时进行有界压缩，保持工具消息配对与证据可追溯，压缩后仍能执行和恢复。
从 `27bedf7` 起步，参考 `d88d28b` 但不要求复制其内部实现。

固定内部模型、token 观测和证据夹具，只验证触发、保留、降级与恢复契约，不按摘要文采计自动分。
需区分 prompt 上下文控制与持久化清理；不能为降低输入大小删除唯一的历史证据记录。
对于保护内容本身已超过预算的不可压缩场景，要求明确的有界失败或降级，不要求实现不可能的窗口压缩。

**错误对照**：直接截断消息列表；每轮固定摘要；删除 ledger 来缩小输入；摘要引用了不存在的证据；压缩失败后无界重试。
**人工项关注**：复杂状态职责是否清楚、失败路径是否可解释、是否避免“压缩成功”遥测掩盖实际未触发。

## 14. 其他讨论过的任务与取舍

### 14.1 DirectFetch 优先与回退

这是很有代表性的候选：静态正文成功时优先直接获取，失败、内容不足或不适用时回退，安全重定向与脱敏保持有效。
但相关 `f2f88fd` 是 51 文件混合提交，其父版本 `c2fb805` 尚无 `DirectFetchClient`，不能包装成“一行调整顺序”题。

暂不作为第一道校准题。后续可从有 router、无直接抓取的起点制作独立“新增 DirectFetch”题，或制作有完整直接抓取但错误优先级的明确故障变体。
后者必须标明人为注入故障，不能伪称真实历史快照。两种题测量的能力与难度不同，不能共用同一 task ID。

### 14.2 请求级自主度覆盖

曾讨论把 request > config > default、默认兼容与 preflight 恒约束作为跨模块题。
当前已有相关实现，可作为历史题储备；由于原提交包含多种能力，首批用新功能 T04 测类似的配置传递与隔离能力，减少答案复现偏差。

### 14.3 连续开发链

候选链：接入新文献来源 -> 增加缓存与失效 -> 修改配置并兼容旧数据。
每阶段保留该模型自己的代码和明确允许的会话状态，不换回参考实现，检验前面的设计是否给后面制造负担。

- 每阶段都有独立冻结需求、验收与预算；阶段结束不自动反馈隐藏测试源码。
- 如允许给阶段结果摘要，所有模型遵循相同协议，链的成绩不能混入无反馈独立任务榜。
- 某阶段失败后仍可继续，记录累计通过阶段数、各阶段分数、回归与救场；不能只统计走到最后的运行。
- 第一阶段起点相同，后续代码不同是该轨道刻意测量的累积效应，不宣称其每一步是相同代码条件下的局部比较。

连续开发与从零重建 ISE 都不进入首版主榜。前者在独立题稳定后开展，后者需要另做需求与架构可替代性研究。

## 15. 框架自身的验证计划

Benchmark 代码也需要测试，不能只测试候选 ISE。

| 测试组 | 关键用例 |
|---|---|
| 清单与版本 | 重复 ID、权重和错误、未冻结、缺 digest、伪造 reference 身份被拒绝 |
| 快照导出 | 新增/删除/二进制/执行位不丢失，秘密和答案文件不进入考场，原仓库不被修改 |
| Git 隔离 | 无原 remote/alternates/参考对象、跨 run 历史和资料不可读 |
| 提交收集 | 改 `.gitignore` 不能隐藏源码，运行中写入无法影响已冻结提交，路径穿越与危险 symlink 被拒绝 |
| 执行环境 | 只允许本次 mock、无真实凭据、依赖和模型资源可离线重建、进程/端口能清理 |
| 外部 CLI 接入 | 无模型名单/usage 也能领题和验收；来源标注、练习/正式分流、首次发题计时正确 |
| 管理式 CLI 调度 | 三种假 CLI、版本拒绝、固定 prompt、无 TTY、授权、幂等、异常事件、后台子进程与监督器重启；真实 smoke 另验 |
| 验收完整性 | 伪造 PASS stdout、删测试、skip、提前退出、重复 check、报告篡改不能得到虚假通过 |
| 分数与状态 | 全过、部分过、关键失败、无提交、开发超时、候选构建失败与设施失败正确区分 |
| 人工评审 | 分数越界、未 PASS 加分、证据不存在、提交不匹配、未评审与零分混淆被拒绝；报告不执行候选脚本 |
| 汇总与复评 | 不同轨道/版本不静默混排，INVALID 不隐去，重评保留旧记录，任务等权不受测试数影响 |
| 端到端 | 同一冻结提交反复 grade 得到相同基础分、判定和稳定证据字段 |

评分器使用小型合成任务先验证：必过项失败但其他分数高、正确功能但输出伪造分数、环境启动失败等情况都能形成正确报告。
在至少 T01 和 T02 的完整闭环完成前，不发布正式模型排名。

| P3-A/B 评审与比较机制 | review schema、个人分录入、批次预登记、aggregate/compare | 加分可审计；不同轨道、版本和缺失结果不会混排；不要求实际组织 pilot 或填入真人分 |
| P3 收尾（P3-C05） | 使用说明与报告复核 | 现有命令组成可复跑的操作链；报告重生成不改原始提交、验收与评审记录 |

下列工作统一进入[可选事项](../../plan.md#optional-work)，无须按阶段编号全部实施：

| 可选工作 | 何时启动 | 选用后的约束 |
|---|---|---|
| 实际 pilot 与个人加分 | 用户需要比较配置或记录个人偏好时 | 批次执行前冻结条件与重复计划；加分由真人填写 |
| P3-C01–C04 纠错与成绩发布 | 需要衡量反馈后修复能力或交付成绩报告时 | 派生 run、统一反馈与额外预算，首次分不覆盖；正式发布须满足发布检查 |
| P4 扩题 | 两题覆盖不足时，可先 T04 再 T03 | 新题各自准入并冻结新 suite；不要求制题时完成模型实测 |
| P5 高难与连续链 | 需要挑战题或长期开发实验时 | 独立轨道和稳定验收；选择实测时再校准难度与成本 |
| 正式发布与维护 | 决定发布正式成绩时 | 补齐正式隔离、资格复核签署和可比性证据，每次发布重新检查 |

选择 pilot 筛选时按每个参测配置每题 3 次设计：两题每配置 6 次；若选择四题 suite 则每配置 12 次，六题则 18 次。日常单次诊断无须先组织整批。不同 suite 不能直接比较总分，不把计划次数写成已执行记录。

首版直接支持用户自选 CLI 的 `agent-native` 流程，不以受控模型框架为前置工程。
框架准备不要求预定 CLI/模型名单或安排计费试跑；用户在实际运行时选择配置，费用由外部 CLI/provider 管理，未采集费用写 null。
默认由管理 Agent 经启动器安排运行，手动模式备用；实际使用的 CLI/profile 仍须通过真实 smoke 并具备运行授权，不需要预先验证所有可选配置。
组织正式批次时再冻结参测配置、共同条件与重复计划；自由 CLI 结果不能包装为模型本体公平比较。

## 17. 风险、限制与待决问题

| 风险 | 处理方式 | 剩余限制 |
|---|---|---|
| 只测单仓库，任务分布偏置 | 修复、功能、跨模块与状态题混合；报告分项 | 仍只代表 ISE 及类似工作负载 |
| 历史答案已被模型见过 | 清理直接泄漏、标记历史题、加入新需求和未公开变体 | 无法证明消除了训练数据污染 |
| 历史提交范围过大 | 抽取行为，显式 preparation patch 与参考分支 | 出题成本增加，不能机械一提交一题 |
| 参考实现也可能有 bug | 先契约后实现，错误对照、替代实现与独立复核 | 通过测试不证明无缺陷 |
| 隐藏测试绑定实现 | 黑盒契约优先，不要求复制私有函数 | 一些深状态不变量需额外适配和验证 |
| Python 白盒裁判可被候选干扰 | 可信控制进程不导入候选；外部断言与调用观察 | 不能把只读测试文件宣传成强隔离 |
| 人工印象污染客观排名 | 独立加分、冻结规则、证据、尽量盲评 | 个人分仍有主观性 |
| 管理 Agent 成为隐形教练 | 固定公开 prompt、禁止自由追加指令、不同会话与权限 | 仍需信任管理员，skill 文字本身不能强制隔离 |
| 设施噪声与选择性重跑 | 原始记录、统一重跑规则、INVALID 补齐 | 小样本仍不稳定 |
| 固定 mock 导致只会应付单一脚本 | 多场景与隐藏变体，公开协议而不公开全部答案 | 不替代真实系统质量实测 |
| 分数高但用户仍不省心 | 同列可靠性、回归、救场、验证真实性与成本 | 实际合作体验还需日常使用验证 |

P0 已确定位置、责任、首版预算、计分和评审政策，详见 [决策记录](p0_decisions.md)。
选择正式发布成绩时须核对以下实施验证，具体完成状态见计划中的最新证据；这些门槛不因发布工作移至可选部分而取消：

1. 按决定部署私有区域并实际验证容器、网络、权限、资源和秘密边界。
2. 验证 Codex/pi/Claude 进程适配、监督器、管理接口与元数据；未完成正式接入 smoke 的配置不能宣布已兼容，不需预先覆盖所有模型。
3. 对首批参考版本验证资源和时间可行性，冻结镜像与任务预算；其他题在各自准入前确定预算。
4. 把 60/25/15 和全部必过项落实为可信 checker；人工 10 分落实为可审计的独立评审记录。
5. 冻结 T01 输入域、T02 导出契约；T03-T06 的详细契约随各自阶段完成。
6. 真正完成非参考作者的资格复核；没有实际签署不能发布题目，个人加分可以跳过。
7. 实现日志脱敏、保留与清理审计，以及参考实现公开后的题目退役和版本维护。
