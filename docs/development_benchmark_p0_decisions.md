## 1. 本次确定的边界

用户需要的流程是 **指定任务与 CLI/模型 -> 管理 Agent 启动考场和被测 CLI -> 自动收卷 -> 脚本验收 -> 可选个人加分**。
框架负责试卷、CLI 进程调度、提交与裁判，不负责选择模型、重写 CLI 推理循环或评价模型自己的回答。
手动领取任务、自行启动 CLI 仍作为备用入口。具体调研、命令和适配契约见
[管理 Agent 与 CLI 调度设计](development_benchmark_cli_orchestration.md)。

本次用户明确：

- 模型和 CLI 在实际使用时选择，不应成为框架准备的前置条件。
- 当前只做离线准备，不安排计费试跑。
- 不需要模型自评，人工评审应当方便完成。
- 后续补充：管理考试的 Agent 可以通过命令行调用 Codex、pi 或 Claude Code，不必由用户手动打开每个被测 CLI。

据此撤回此前“首版必须固定 mini-swe-agent、模型名单和 API 适配”的建议。
本系统不依赖该框架，也不安装它。受控模型实验保留为可选扩展，不阻塞 P1/P2。
本次增加的是三个原生 CLI 的进程适配器，不是模型 API 适配器。

| P0 项 | 决定 | 落地阶段 |
|---|---|---|
| P0-05 | 同机私有控制区、源快照与产物分别存储；Agent 不获得宿主访问权 | 第 2 节；P1 建立存储，P2 验证边界 |
| P0-06 | 正式目标为 `isolated-formal`；保留任意 CLI 的 `local-practice` 入口 | 第 3 节；P2 实现与实测 |
| P0-07 | 首版 `agent-native`，默认 `managed-cli`；模型/CLI 由用户选，`manual-external` 备用 | 第 4 节及 CLI 调度设计；P2 实现，P3 按实验冻结 |
| P0-08 | 首批两题采用固定时间与硬件配额；不托管模型费用，不要求工具调用计数 | 第 5 节；P1 校准，P2 实施 |
| P0-09 | 客观 60/25/15，六项均必过；个人加分 4/3/3，最高 10 | 第 6 节；P1 制题，P2/P3 验证 |
| P0-10 | 维护者承担资格复核；个人加分按需评审；短报告、证据索引和机器校验 | 第 7、8 节；P1 复核，P3 实现评审流程 |

“P0 完成”表示规则和责任边界已经确定，不表示目录、分支、镜像、配额或评分器已经存在。
下列工程默认值在首次冻结试卷前可以根据离线资格测试修订；修订必须更新版本，不能在看到被测成绩后调整。

## 2. 部署、权限与分支

首版使用当前 Linux 主机，不要求先购买独立主机或接入 Git 托管服务。

| 位置 | 内容 | 访问主体与约束 |
|---|---|---|
| `/home/ubuntu/code/ISE` | 正常产品仓库 | 不挂入考场，不创建参考分支或自动合入候选代码 |
| `/home/ubuntu/.local/share/ise-devbench/controller` | 私有 `ISE-devbench` Git 仓库、任务契约、裁判 | 可信维护者 `ubuntu`；目录 0700，敏感文件 0600 |
| `/home/ubuntu/.local/share/ise-devbench/source.git` | 私有源快照 Git 仓库、base/reference/mutant 对象 | 仅可信准备区访问，不向 Agent 暴露对象库或 remote |
| `/home/ubuntu/.local/share/ise-devbench/artifacts` | 冻结快照、提交、验收、评审与报告 | 控制器写入；评审者只取得指定的脱敏评审包 |
| `/home/ubuntu/.local/share/ise-devbench/runtime` | 本次任务临时卷、mock 与沙箱状态 | 控制器管理；只把本次公开资料和可写工作卷交给对应沙箱 |

P0 只确定位置，这些路径在本次检查时均未创建。无需在 ISE 主仓库中新增框架实现目录。
私有仓库首版不配置公开 remote；需要备份时只能另设维护者控制的私有备份。

首版可信管理员与控制器均由 `ubuntu` 执行；此用户属于 Docker 组，必须按高权限信任主体处理。
**0700 不能防住同一个宿主用户运行的 Agent。** 正式隔离来自容器挂载、网络、进程与权限边界，不来自目录分开。
正式开发及候选执行进程默认使用容器内非 root UID `10001`，不得访问宿主 home、Docker socket 或控制器服务。
评审者身份是应用层记录，不意味着已建立独立 Unix 账户。

分支规则沿用系统分析第 6 章：

- 控制仓库：`main`、`bench/ise-v1`，发布标签 `suite/ise-v1.0.0` 不可覆盖。
- 私有源仓库：`bench/base/T01/v1`、`bench/reference/T01/v1`、`bench/mutant/T01/<case>`；T02 同理。
- 考场：从净化文件树重新初始化 Git，只含 `run/<run_id>` 的起点与本次改动，无原仓库历史。
- 提交身份：受控文件 manifest 和归档摘要，不是可移动的工作分支头。

P1 才制作分支与三件套；不为完成 P0 空建未经资格验证的“正确答案”版本。

## 3. 自由 CLI 与正式隔离的边界

| 使用方式 | 能做什么 | 成绩资格 |
|---|---|---|
| `local-practice` | 导出题目到独立本地目录，用户自行选择 CLI；提交后仍可独立重建和自动评分 | 单次诊断报告，标明开发环境未受控，不进入正式可靠性排名 |
| `isolated-formal` | 在受限沙箱中领取同一题目，控制器启动用户选定且已准入的 CLI；计时、冻结与验收均由控制器完成 | 通过实际隔离检查后，进入 `agent-native` 正式比较 |
| `model-controlled` 扩展 | 在正式隔离基础上额外固定 Agent 框架与配置，只替换模型 | 才能进一步讨论模型本体差异；不属于首版必需功能 |

不能把“任意 CLI”解释成“任意权限仍有相同可信度”。在原 ISE 仓库旁以宿主同用户无限制运行、
接入已有个人会话或可读参考答案时，依然可以检查产物，但不能证明独立解题。
即使验收本身独立，开发阶段的答案泄漏也不会因此消失。

正式接入条件不指定 CLI 品牌，但要求：

- 只访问本次净化工作区、公开资料和允许服务；使用新的 HOME、配置与会话，不读取个人记忆。
- CLI 安装层预先准备并记录版本；应用 `env1` 依赖和公开测试契约不随 CLI 改变。
- 不挂载宿主登录资料。真实 provider 凭据留在候选区之外；可由兼容的外部网关提供限本次运行的连接。
- 开发 CLI 与其工具若共享沙箱，不能声称其中的短期网关凭据对候选代码保密；网关必须限用途、限运行并可撤销。
- 不满足凭据/网络隔离的 CLI 仍可走本地练习入口，不能悄悄降低正式模式门槛。
- 正式验收区不安装或启动开发 CLI，不获得外层模型网关权限，只访问本次内部 mock。

外层网关是可选部署接入设施，不是模型选择器或必需的推理框架。
本期离线准备使用不调用真实模型的模拟开发进程测试考场闭环；不承诺所有商业 CLI 已可正式接入。

容器启动要求：非特权、移除 capabilities、禁止提权、独立 PID/网络、受限挂载、资源配额和默认系统调用约束。
不运行候选提供的 Dockerfile 或可信宿主脚本。容器仍共享内核，首版不宣称达到独立虚拟机的对抗保证。

## 4. 领题、执行与记录

首版默认执行方式为 `managed-cli`：管理 Agent 使用控制项目内的管理 skill，调用 devbench 启动选定 CLI。
框架不直接实现 provider/模型 API 适配器，但需要对 Codex/pi/Claude 的命令、日志和退出状态做薄适配。
任务与验收接口仍是公开任务书、快照、提交归档和标准结果，不绑定某个 CLI 的内部推理实现。

默认拟定流程，命令尚未实现；`run` 自动编排准备、启动、收卷、验收与报告：

```bash
python -m devbench run --task T01 --version 1.0.0 --profile pi-work --run trial-001 --dry-run
python -m devbench run --task T01 --version 1.0.0 --profile pi-work --run trial-001 --execute --authorization approval-001
python -m devbench status --run trial-001
python -m devbench report --run trial-001
```

授权引用须由控制器核验，本次尚未批准真实模型运行。管理 Agent 不得把自己的会话、参考答案或临时解题建议传入启动 prompt。
监督器独立于管理会话持久运行，避免管理 Agent 断线后丢失截止时间；详见 [调度生命周期](development_benchmark_cli_orchestration.md#lifecycle)。

备用的 `manual-external` 流程保留：

```bash
python -m devbench prepare --task T01 --version 1.0.0 --run trial-001 --isolation local-practice
# 在返回的工作区中，使用自己选择的 CLI 完成公开任务。
python -m devbench submit --run trial-001 --participant participant.json
python -m devbench grade --run trial-001
python -m devbench report --run trial-001
# 需要个人加分时才进入评审。
python -m devbench review prepare --run trial-001
python -m devbench review record --run trial-001 --file review.json
```

`prepare` 的私有准备可以提前做，但首次向用户交付可读试卷前必须记录 `RUNNING` 和起始时间。
不能先给完整任务、无限期思考后再启动计时。正式模式由控制器在限时到达时停止写入并冻结产物；
本地模式要求用户先结束 CLI 写入，只记录可观察到的时间，不能伪装成已强制执行的开发预算。

管理运行从已确认 profile、CLI 探测和实际事件生成参测记录，分别保存 requested 与 reported 模型身份及信息来源。
手动运行的 `participant.json` 由操作者提供，包含 CLI 名称/版本、模型/provider 声明、可见设置与人工介入记录。
该来源标为 `operator_declared`；CLI 自报同样不能当作已被独立验证的 provider 事实。
不要求 API 密钥，不复制登录配置，不要求提交私有推理过程；必要开发证据是可见命令、输出与交付说明。

可获得的信息应登记，无法获得的模型版本、内部提示、token 或费用写 `unknown`/`null`，并记录覆盖率。
缺少这些信息不阻止领取任务或验收代码；但关键开发条件无法确认的记录只展示单次结果，不冒充受控比较。
同一 CLI 中途切换模型时记录组合配置，不能将混合完成的提交归到单一模型名下。

正式比较按“CLI + 模型 + 配置”识别参测对象，模型名单在组织比较实验时确定。
同一参测对象的配置必须在重复运行间保持一致；不同 CLI 本来就是 `agent-native` 中允许比较的变量。
共同固定的是题目、可见资料、环境契约、配额、反馈和重复次数，不要求不同 CLI 的内部工具实现完全相同。

首个比较协议仍为 T01、T02 各独立运行 3 次，全部保留；单次尝试不必预先凑齐名单或运行次数。
P3 组织正式比较时才登记参测名单和批次，未补齐时明确显示暂定结果。

## 5. 时间、资源、资料与费用

以下是首批题目的 `pilot-native-v1` 初始预算，不是已经验证可运行的镜像参数。

| 项目 | T01 | T02 |
|---|---:|---:|
| 开发墙钟上限 | 45 分钟 | 90 分钟 |
| 每次自动验收墙钟上限 | 10 分钟 | 20 分钟 |
| 开发或候选执行容器 CPU 上限 | 2 核 | 2 核 |
| 开发或候选执行容器内存上限 | 3072 MiB | 3072 MiB |
| 开发或候选执行容器进程数上限 | 256 | 256 |
| 单次沙箱可写空间总上限 | 4 GiB | 4 GiB |
| 单次源码提交上限 | 256 MiB | 256 MiB |
| 工具调用、模型调用与 token 硬上限 | 不设通用限制；可采集时附报 | 不设通用限制；可采集时附报 |

不依赖各 CLI 自报的调用次数执行公平性门槛。首版以可外部执行的墙钟和资源限额为共同约束，
没有统一计数通道时不能声称限制了模型内部调用。未来等 token/等费用实验另设配置，不混入本档。

同机最多一个开发或验收任务活动；进入验收前停止开发沙箱，不让两者同时占用完整配额。
可信浏览器、mock 和驱动另留合计 1 GiB 预算；主机可用内存低于 4.5 GiB 或磁盘空闲低于 20 GiB 时不接新运行。
准入检查不得通过关闭其他用户服务、清理未知文件或占满 swap 来达标；负载异常记录为设施观察。

磁盘上限须在 P2 使用已验证的配额或有界文件系统落实，包含可写层、临时空间及候选可增长日志。
不能假设当前 `overlay2` 可直接使用容量参数，也不能把定时 `du` 检查称为硬限额。
若主机不能落实限额，正式模式拒绝启动；练习模式明确标记未执行的限制。

依赖与资料：使用题目冻结的 `env1`，依赖、离线官方文档、mock 协议和必要模型资源在发布前准备。
首批默认不新增联网依赖；所有参测对象获得相同的公开资料，不开放网页搜索、原仓库远端和答案检索。
CLI 自身连接外层模型的必需流量是单独声明的例外，不等于 ISE 应用可以访问公网。

首次独立交付不允许人工定位错误或指导修复；合理的需求澄清单独登记。
澄清只重复公开契约已有信息；发现语义缺口应暂停该版本的比较、修订任务并统一重跑，不为单次运行补答案。
人工纠错可以另开派生 run，原成绩不覆盖。首版禁用子 Agent、个人记忆和跨运行答案缓存；不兼容者留在练习模式。

费用政策：**本期由 benchmark 发起的计费调用为 0，不安排真实模型试跑。**
以后默认由管理 Agent 经控制器启动用户选定的 CLI，其订阅/API 花费仍在 CLI/provider 侧结算。
自动启动前须批准具体任务、profile、次数与时限；不能因为没有直接调用模型 API 就免除授权要求。
本框架不承诺跨 CLI 的统一金融硬限额，只附报有来源的 usage，缺失为 `null`。
如增加按费用预算的自动批次或付费网关，必须另行确定计量与限额方式；本次 P0 不授予计费运行权限。

## 6. 分数与硬门槛

首批两题沿用系统分析中的 6 个行为验收点：功能 20+20+20、边界 15+10、回归 15，总分 100。
六项全部 `required: true`，且产物、构建和评测完整性必须合格；不另设 80 分等通用及格线。
因此首批 PASS 应为 100 分，部分分用于诊断缺口；这不是能用加分补救的“及格考试”。

正式比较同时显示平均基础分和独立交付成功率，不能只展示总分。
`FAIL` 是有效失败，进入计划运行的分母；`INVALID` 基础分为 `null`，记录原因并统一补跑。
练习运行的评分规则相同，但单列隔离和资格标识，不进入正式可靠性统计。

人工项沿用可维护性 0-4、范围控制 0-3、交付清晰度 0-3，最多加 10 分，仅 PASS 有资格。
未评审为 `null`；完成评审但没有加分为 0。客观榜不受人工加分影响，个人榜不混排未评审结果。
T01/T02 的详细输入域仍由 P1 制题冻结，不在 P0 将尚不存在的 checker 标成已验收。

## 7. 轻量评审流程

### 7.1 责任分离

| 角色 | 默认责任 | 不允许做的事 |
|---|---|---|
| 出题实现者 | 制作契约、reference、grader、错误对照和资格证据 | 仅凭自己的测试结果签署独立复核 |
| 项目维护者，默认用户 | P1 资格复核的最终责任人；可另指定非该参考实现作者的复核者 | 将尚未完成的复核登记为已通过 |
| 个人评审者 | 用户本人或其明确指定的人，在提交评审时登记身份 | 改自动分、通过状态或验收规则 |
| 报告脚本 | 汇总可信自动结果、差异、截图、证据索引，校验人工填写 | 生成主观加分或信任候选自报的“测试全过” |
| 协助整理的助手 | 整理证据；用户明确给分后可代录 | 代替用户评价并自动签署个人分 |

没有模型自评步骤，也没有 LLM judge 自动评分步骤。被测 Agent 的交付说明只是待核实材料，不是判定依据。
资格复核不是每次试跑都做一次，而是在题目发布或实质变更时做；个人加分则完全可跳过。
如果维护者本人编写了 reference，需指定另一复核者；无人完成独立复核时该题不能进入 `frozen`。

### 7.2 一次评审的实际操作

1. `grade/report` 自动完成基础分与 PASS/FAIL/INVALID，不等待人评分。
2. `review prepare` 生成匿名评审包：一页摘要、分项验收表、代码 diff、证据索引和预填身份的空评分表。
3. 先看失败和完整性问题。FAIL/INVALID 只做诊断，不出现可提交的加分入口。
4. PASS 时查看主要 diff；T02 直接附桌面/移动截图、下载验证和错误态证据，不要求重新手工走完整回归。
5. 用户可以选择不评；要加分时只填三个分项及简短理由，选择已有证据 ID，无需手写 hash 或找日志行号。
6. `review record` 校验后追加记录，重新生成个人报告；分值由脚本相加，自动结果保持不变。

首版采用静态 Markdown/HTML 报告、JSON 表单和命令行导入，不先建设 Web 管理台。
报告按摘要、失败项、差异、截图、原始日志逐层展开，原始日志只是最后的追查入口。
用户可直接告诉助手“这份评审的三个分项和理由”，由助手写入表单并运行校验，但必须保留真实评审者与代录来源。

表单预填 task/version、submission/evaluation/rubric、匿名 review ID；评分初始为 `null`，不默认赠送任何分数。
证据索引使用稳定 ID，映射到冻结提交的 diff 区块、受控截图、自动验收项或可见交付记录。
导入拒绝缺分项、非整数、越界、缺理由、证据不存在、路径越界、身份不匹配和非 PASS 加分。
交付记录缺失时标记不可核实，不用缺日志直接证明 Agent 作假。

### 7.3 盲评、争议与安全

默认报告隐藏 CLI/model/provider、文件归档中的身份标签和运行顺序，以随机评审 ID 展示。
不能为了盲评改写代码或删除与判断有关的事实；代码风格、熟悉的运行过程可能暴露身份，实际记录 `blinded: false/partial/true`。
用户亲自运行并记得模型时允许非盲评，不能谎报双盲。

首版每份评审只有一位指定评分人；未来多评审者必须在评审前冻结聚合规则，不能择高分。
发现自动验收漏项时登记争议、暂停排名资格并转入裁判复核；修复 grader 后一致重评，不用人工扣/加分修改 PASS。
评审修订追加版本并保留旧记录；代码或 evaluation 变化后旧评审不能静默复用。

报告生成器将候选代码、日志、Markdown 和文件名视为不可信文本：转义 HTML，禁止自动执行或加载外部资源。
截图及下载由隔离浏览器采集；需要复看应用时另建隔离预览，不把候选页面与控制区共用 origin、cookie 或文件访问权。
人工评审也不能成为执行候选代码、读取任意宿主路径或泄漏参考答案的新通道。

## 8. 证据保留与可复现性

- 私有题包、base/reference/grader 和环境锁定产物：至少保留至对应题目退役后 1 年。
- 原始提交和完整开发/验收日志：每次运行后保留 90 天；需要长期复现的运行必须在到期前明确归档延长。
- 脱敏报告、分项结果、manifest、评审及审计记录：保留至少 1 年。
- 存储位置沿用第 2 节，默认仅可信维护者访问；评审者领取指定脱敏包，不直接浏览整个 artifact store。
- 不保存真实 API 密钥、登录 cookie 或个人数据库。发现意外泄漏时撤销凭据并生成脱敏修订，保留最小事件记录，不扩散秘密。
- 到期清理须由维护者显式执行并记录，不能在 P0 删除现有文件。清理后将相应结果标为 `replay_available: false`，不再宣称可复跑。

比较报告不能把“有摘要”说成“仍保留可重建提交”；旧证据不足时仍可保留历史记录，但不得参与要求可复现的正式重评。

## 10. 决策修订

`p0-v1` 首先将“框架固定模型”改为用户自选 CLI，并采用手动执行入口。
用户随后要求管理 Agent 能通过命令行调用 Codex/pi/Claude，因此 `p0-v2` 将默认执行改为 `managed-cli`，
保留手动入口，不改变题目、分值、分支、隔离与模型由用户选择的原则。
本次核对三者官方文档、本地帮助和版本；CLI 调度文档记录版本差异，P2 增加适配器、监督器和管理 skill 待办。
